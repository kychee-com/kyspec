Specs with the code. Changes are born to be deleted.

Git is the history. The model is trusted. Kyspec is the OpenSpec spin-off we use at Kychee to build run402, our open-source backend for AI agents, and our other products.

It puts each change in one file, updates the spec in the same commit as the code, and requires a fresh agent to test the released product before user-facing work is finished. When the work is done, the requirements and decisions live in the spec. The change file is deleted. Git keeps the history.

The rails were built for a weaker model.

OpenSpec, Spec Kit and their peers were designed in 2025 for models that lost the thread: a CLI to validate what the model wrote, templates to fix the shape of every artifact, an artifact graph to say which file it may write next, delta files to keep its hands off the main spec, and an archive so nothing it produced was lost. Those were sensible answers at the time, and OpenSpec’s distinction between the current spec and the work that changes it is one we still build on.

The model changed. The scaffolding did not. A frontier model in 2026 reads a long spec, the code it governs and the git log, and writes the new requirement in the spec’s own voice. For that model the rails now cost more than they save, in five places:

  1. Expressibility. A template gives every change the same four files, whether it renames a field or adds a subsystem. In Kyspec a change is one file with seven sections, any of which may be one line.
  2. Throughput. An artifact graph serializes thinking into proposal, then specs, then design, then tasks, each a round trip through a tool. In Kyspec each step is one page, and the model does the step.
  3. Imagination. Delta blocks make the model think in text diffs instead of system behavior. Kyspec starts with a brainstorm whose partner challenges rather than flatters, and the plan must search prior art and mark each hit keep or override.
  4. Implementation quality. A merge nobody reads lets the spec drift from the code within weeks. In Kyspec the model edits the main spec in the commit that satisfies the requirement, and a fresh agent that never saw the diff checks the released product the way a user would.
  5. Context quality. An archive of dated proposals is dead weight in every grep and every context window. Kyspec deletes the change once the spec has absorbed it and leaves the history to Git.

Loosening the shackles is not lowering the bar. The bar moves from the shape of the artifacts to the truth of the spec and the evidence of the release.

Kyspec trades validation for gates and narrative for evidence: a task line carries a SHA, a count or a dated live check, or it is open, and done means verified by someone who did not build it. The whole argument is in WHY.md.

Three tiers, one unit of work, five skills, one gate.

The agent reads five short skills and edits ordinary Markdown files. Product-specific instructions live in AGENTS.md. A dependency-free Node.js check covers the required layout; review and verification cover meaning and behavior.

Three tiers

Principles, numbered so specs can cite them. Specs, one per capability, in the present tense: stable requirement names, WHEN/THEN scenarios, and Design notes holding decisions under D-<capability>-N ids. Ideas, one file each, whose first line is its status.

One unit of work

A change is one file, changes/<name>.md, with exactly seven sections: Why, Specs, Prior art, Decisions, Tasks, Surface review, Verification. Each can be one line. Once its requirements and decisions are settled into the live specs, the change is deleted.

Five skills, one gate

Brainstorm, plan, implement, verify, finish: one short page each, no templates fetched at run time, no artifact graph. check-layout.mjs checks the structure of changes and ideas in CI, including the rule against archived or date-prefixed changes.

A commit that touches no spec and carries no decision, such as a typo, a dependency bump, or a test fix, needs no change file.

The chain

Five skills run the method. Each accepts the change or idea name and ends by naming the next step, so the chain runs from “implement owner/repo#N” in one coordinating thread. Verify alone runs in a fresh agent.

StepSkillResult
1kyspec-brainstormStarts or continues an idea file and always ends in one.
2kyspec-planWrites the change file.
3kyspec-implementWorks the tasks, pushes, records CI, then runs the product’s Release skills and records their evidence.
4kyspec-verifyChecks the released product in a fresh thread without reading the code or diff.
5kyspec-finishSettles the change into the specs and deletes it.

A sixth page, kyspec-migrate, is outside the chain: a repository arriving from OpenSpec runs it once, on a branch.

A change’s life

Consider the reading-list example in examples/lantern: a reader should be able to archive a book and restore it without losing its notes or reading status.

StepWhat happens
PlanOne change records the requirement, relevant prior decisions, tasks, and verification scope.
ImplementThe requirement lands in the main spec with the code. The builder records CI and release evidence.
VerifyA fresh agent archives an in-progress book and restores it through the released product. The book returns, but its previous reading status is lost.
FixThe verifier records the failure and adds a task. The builder fixes the behavior and releases again.
FinishA new verification cycle passes. Lasting decisions move into the spec, and the change file is deleted.

The task list was complete. The user’s workflow still failed. Kyspec makes that check part of finishing.

The example workflows walk through this change and four other situations: a fix that needs no change file, the whole chain from an issue, a brainstorm that parks, a verify that fails, and two sessions on one repository.

Compared with OpenSpec

This compares Kyspec’s method with OpenSpec’s documented standard workflow. OpenSpec supports customization; these are the choices Kyspec makes for you.

ConcernOpenSpecKyspec
Updating the current specDelta specs merged through sync or archiveMain spec updated in the implementing commit
Checking implementationOptional, report-only verification against artifacts and codeRequired fresh-thread check of released behavior for changed user-facing flows
Finishing a changeMove the change to an archive directorySettle requirements and decisions, then delete the change

The full comparison, with sources checked October 2026, is in WHY.md, which also explains the tradeoffs and what prompted us to switch.

Try Kyspec on your next change

Start with a small change you already need. The useful test is whether the next session can see what changed, why it changed, and how it was verified. Four files, three lines: 

git clone https://github.com/kychee-com/kyspec /tmp/kyspec
cp /tmp/kyspec/METHOD.md /tmp/kyspec/check-layout.mjs .
cp -r /tmp/kyspec/skills/kyspec-{brainstorm,plan,implement,verify,finish} .claude/skills/
  1. Copy the method and skills. METHOD.md goes to your repository root. The five chain directories under skills/ go into your coding agent’s skills directory, preserving each SKILL.md: .claude/skills/ for Claude Code (/kyspec-brainstorm <topic>), .agents/skills/ for Codex ($kyspec-brainstorm <topic>). For another host or a cloud session, use its supported skill installation mechanism. A repository arriving from OpenSpec also takes kyspec-migrate, for one run.
  2. Declare your product’s rules. Add ## Method declarations to AGENTS.md and name the documents and skills your product actually uses. Omit declarations that do not apply; the method defines their behavior in Method declarations. 
    ## Method declarations

- **Principles:** docs/principles.md, numbered; specs cite principles #N.
- **Release:** /deploy for the API and site; /publish for the npm package.
- **Surface review:** /review-api for src/api/** and openapi.json; judge against docs/api-principles.md.
- **Coordination room:** the channel and procedure for claiming an area and announcing completion.
  3. Add the layout check (recommended). Run node check-layout.mjs in CI. It checks the structure of changes and ideas, including the rule against archived or date-prefixed changes. Reviewers and the finish workflow assess the requirements and evidence.
  4. Start the work. Invoke kyspec-brainstorm for an idea, or ask your agent to use Kyspec to implement a named issue. The skills carry the work through planning, implementation, your release process, verification, and finishing. Verification of a changed user-facing flow runs in a fresh thread with access to the released product; that independent check is part of the method.

Or let your agent do it: paste this into your coding agent’s chat.

Set up Kyspec in this repository: clone https://github.com/kychee-com/kyspec, copy METHOD.md and check-layout.mjs to the repository root and the five kyspec-* chain skills into the skills directory, then add "## Method declarations" to AGENTS.md as https://kyspec.com/METHOD.html describes.

Moving from OpenSpec

Keep your requirement prose and WHEN/THEN scenarios. Change where the knowledge lives and how work finishes.

The full map, artifact by artifact, is MIGRATING.md, and the sixth skill, kyspec-migrate, runs it on a branch and records the migration as your first change. examples/migration shows one repository before and after. The transition is a repository edit; in outline:

  1. Reconcile the current behavior. Fold already implemented delta requirements into the current specs. Keep unimplemented proposals separate.
  2. Move the specs into the Kyspec layout. Keep requirement names and scenarios, and update links to moved specs.
  3. Convert active changes to changes/<name>.md with exactly the seven sections.
  4. Keep the decisions. Move still-relevant design decisions into the owning spec’s Design notes under stable D-<capability>-N ids, and repoint code, test, and documentation references.
  5. Retire completed plans once their lasting requirements and decisions are retained.
  6. Switch the instructions and check the layout. Install the skills, add your declarations, update agent instructions to use Kyspec, and run the layout check.
Migrate this repository from OpenSpec to Kyspec: read https://kyspec.com/MIGRATING.html, install the kyspec-migrate skill from https://github.com/kychee-com/kyspec, and run it on a branch.

How we use it at Kychee

Kyspec grew out of our day-to-day work on run402. We had shipped changes whose spec deltas still needed promotion, and code that cited decisions in archived plans. We wanted current contracts, durable rationale, and an explicit check of the released experience.

This is the method we now use at Kychee, with parallel Claude Code and Codex sessions. Our release, review, and coordination details became declarations so you can use the same method with your own stack. Kyspec does not require run402.
